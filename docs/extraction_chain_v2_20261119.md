## 修复后的行为

| 问题 | 新版行为 |
|---|---|
| 原2600字符来源包可能产生超过9000输出token的候选JSON | 新包按900个原文字符打包，保留完整段落，输出额度12288；单段超目标时显式记录，不截断原文来凑大小。本次38包均未超900字符。 |
| 末尾截断被JSON解析异常掩盖 | 先检查length等终止原因，明确记录output_incomplete；不把截断当作来源事实错误，不自动重试。 |
| 流式中断后没有保存已经收到的可见输出 | 第一批可见内容、约1秒/2048字符的进度及终态写入原attempt的SQLite事件。只保存公开回答内容和诊断计数，不保存私有推理文本。 |
| 计量包装器导致原生客户端不能通过独立进程分支判断 | 新抽取路径使用原生客户端交给已有独立request_worker，使用SQLite请求账本计量，避免落入守护线程分支。 |
| 调用方超时可能覆盖早已收到的请求标识 | 进度记录提前保存响应ID；超时收尾缺ID时保留已有ID，客户端跟踪ID随原请求发送。 |
| 已收完整对象因外层JSON不完整而全部丢弃 | 自动保留可完整解析的可见前缀对象，再逐条做schema和原书锚点核对。原请求仍保持截断或未知状态，不伪造完整回复或覆盖结论。 |
| 环境配置变化可能使抽取客户端偏离冻结设置 | 执行前核对模型、目的地、流式开关、超时及输出额度；与extractor_settings.json不符时在派发前停止。 |

900字符是来源文本长度，不包含包内来源标记和本体上下文。小包降低输出截断风险，不能保证提供方永不超时；本轮没有用新增真实调用证明服务端时延已恢复。

旧流程中计量包装器造成的守护线程回退是已确认的持久化缺口，但它不能被当成此前HTTP 200后正文超时的服务端根因证明。原始unknown仍待服务端证据对账。
