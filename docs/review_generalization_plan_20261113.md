## 工作如何分流

| 发现的问题 | 后续处理 | 验收对象 |
|---|---|---|
| 契约、引用、预算、超时对账、状态传播等代码缺陷 | 按原因定位代码，形成适用于其他 ID、文本及端点的修复 | 同类变体和正反例的行为；有效语义分歧仍被保留 |
| 原文不足、定义缺失或错误、本体不覆盖 | 系统准确识别、补检索、生成带来源的待办或隔离提案 | 识别与处置正确；不要求当场补齐全部知识 |
| 合法且有实质理由的模型分歧 | 保留原票、记录具体争议和不可判定项 | 不因未一致就反复改措辞或重评到批准 |
| 指标或验证设计缺失 | 分开工程结果、语义结果和判定覆盖，建立新材料验证 | 有绑定清楚的标签和独立来源，结论不超出证据 |

## 后续顺序

1. 从既有轨迹整理跨样本原因，关联实际代码位置。区分代码缺陷、知识缺口、模型分歧与评价盲区，不再按 DEV 编号逐条追求通过。
2. 对有证据的共性代码缺陷做最小修复。用其他实体、关系、类型和条件的正反例验证；不能仅替换样本编号或改预期值。必要的数据纠错另存新版本，不反改历史基线。
3. 保留 30 条作为固定开发回归。代码、契约、提示词、已批准本体与评价口径冻结后，做一次可对照回归；不要求 30 条全部准入。
4. 从未用于调试的章节或文档建立独立验证材料，按文档来源和重复事实分组隔离，记录其是否曾参与调试。规模与采样规则先确定，再执行；尚未选取或宣称拥有独立测试集。
5. 分别报告契约完整率、原文支持判断、映射质量、必要修订及修订后正确性、合理转人工和可避免转人工、调用与 token 成本。各指标说明标签来源和可判定分母；AI 辅助标签不写成人工金标，缺独立标签时不宣称准确率改善。
