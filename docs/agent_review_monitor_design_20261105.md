# Agent 审核与独立模型意见的前端展示设计

本方案已于2026-11-05接入工作台。实现与验证记录见 agent_review_monitor_implementation_20261105.md；监控读取生产和已登记实验的记录，不触发模型调用。

## 现状与原因

当前工作台默认连接 runs/v3/review.sqlite3，本次30条V6.2实验则在 outputs/dev30_v62_rerun_20261105/review.sqlite3。两者包含相同候选标识时，审核记录仍属于不同数据源，不能仅靠 candidate_id 混用。

TripletReview.vue 已有折叠的“Agent 调查过程”和简短的模型意见；service.items 也会返回 planner_steps、tool_calls、votes 等信息。当前定时器仅刷新抽取任务，没有订阅审核运行状态。

另一个缺口是 request_summaries 从已有 votes 的 request_key 查请求历史。模型已发出请求但尚未形成持久化票时，这条路径无法展示正在运行、已返回待校验等状态。完整 audit 接口也不直接包含实时请求记录。

列表会优先选择最近决策所属的 audit，可能掩盖更新的在途审核。监控页须明确区分“本次运行”和“已有有效结论”。

## 页面布局

新增一级页签“Agent 审核监控”，从现有候选详情也可打开相同审核详情。

1. 顶部选择数据源和批次，实验源明确标记“实验库、只读”。显示总量、已开始、处理结束、三席审核齐全、审核未完成、真实分歧等计数；处理结束和审核齐全是两项指标。
2. 左侧候选列表：样本ID、候选版本、当前阶段、可用席位数。可按运行中、未完成、有分歧、需修订筛选。
3. 中部 Agent 时间线：公开决策摘要、所选工具、开始/结束时间、工具执行状态、获得的新证据、当前阻塞原因。明确区分“模型提出动作”和“工具确已执行”。基于真实已保存事件排序；无法确定的时间不编造。
4. 右侧三模型对照：Qwen、Gemma、DeepSeek 各一席。顶部是请求执行状态，下面是九维度意见矩阵；点击单元格查看该模型的公开意见摘要、证据ID及原文。程序汇总结果放在独立区域。
5. 补正详情：原响应、字段错误列表、补丁和合并结果可对照；突出补正路径、已用次数及“既有判断未改变”。不把补正当成新增一席。

九个维度沿用当前协议：来源支持、实体指称、关系语义、关系方向、限定完整性、证据充分性、反证处理、正式映射、知识范围。不要要求模型额外产生总票；模型维度意见和程序最终处理状态分开显示。

Qwen 规划角色和 Qwen 独立审核角色分开标识。规划动作不计入三个审核席位。时间线只显示公开动作摘要、调用和观察，不展示模型隐藏推理或完整内部提示。

## 状态语义

|显示状态|含义|是否计入有效审核席位|
|---|---|---|
|排队/请求中|请求未完成|否|
|已返回待校验|收到响应，尚未完成原契约校验|否|
|已校验|同一冻结版本上的有效意见，包含反对和不确定意见|是|
|字段补正中|原响应存在可安全补齐的具体错误|否，待补正后校验|
|格式校验失败/额度耗尽|自动纠错已停止|否|
|请求结果未知|如504，服务端实际执行情况尚不明确|否；不计反对，不自动重发|
|真实分歧|有效模型意见之间存在分歧|各有效席位仍计入；是否准入由程序决定|
|历史/失效|不同候选版本、本体版本或证据包上的意见|不计入当前轮次|

“三席已返回”“三席审核齐全”“程序允许准入”分别显示，不能用一个“审核完成”概括。结构正确的反对意见保持原样，不提供一键重投以消除反对的操作。未知请求只显示对账状态；任何恢复操作均沿用后端既有约束。

## 数据接入

建议增加独立、只读的 review-monitor 查询层，不把实验票导回生产库。数据源用服务端登记的 source_id 选择，不接受浏览器传入任意数据库文件路径；实验只读连接不执行初始化、迁移或后台消费者。

建议接口：

- GET /api/review-monitor/sources
- GET /api/review-monitor/batches?source_id=...
- GET /api/review-monitor/batches/{execution_id}/summary?source_id=...
- GET /api/review-monitor/audits/{audit_id}/snapshot?source_id=...&after=...

快照返回：候选版本、审核/轮次身份、当前阶段、规划步骤、工具调用、每席请求状态、有效意见、程序汇总、停止原因、纠错溯源及更新时间。保留 source_id、candidate_id、revision、audit_id、round_id、proposal_digest、evidence_hash、本体版本等绑定，避免将不同时期的票混在一起。

请求状态直接查询 request_attempts、validation_requests 和绑定的请求元数据，依据 audit_id/round_id/proposal_digest/voter_id 关联；不依赖 validator_votes 已有对应行。原始响应和详细证据按需获取，默认快照不返回完整本体、完整提示、凭据或大量原文。

事件和席位的稳定标识用真实持久化ID，增量游标由服务端生成并返回。请求记录先到、汇总票后到时，前端能合并更新且不重复增加席位。对模型返回、结构校验、补正、程序汇总分阶段处理；尚无阶段记录时显示未知，不猜测中间状态。

迟到响应可以单独标记“已收到，等待原轮恢复采纳”，但监控页不自动改写票或最终决定。当前决定仍以原审核流程持久化的权威结果为准；不能仅根据请求表中已有三份响应就自动展示为允许准入。

## 刷新方式

第一阶段采用前台串行轮询：当前详情约2秒一次，批次概览约5秒一次。页面隐藏或切换数据源时暂停/取消旧请求；网络失败显示最后更新时间和“连接中断”，不据此把模型判为失败。刷新只更新监控状态，保留人工编辑草稿、展开项和已选证据。

生产和实验数据源的切换必须清除前一数据源的请求与缓存，避免同名候选错配。完成后停止高频轮询，或降为低频核对迟到请求。轮询页面没有模型调用副作用。需要更低延迟时再增加SSE，保留刷新后的完整快照和断线恢复机制。

## 实施顺序

先接入实验只读源及实时快照，使本次30条实验可见；再抽取候选监控、Agent时间线、模型状态、九维矩阵、纠错对照等独立Vue组件；最后接入增量刷新及断线提示。第一版只做查询和展示，沿用已有审核、恢复、修订和发布流程。

## 验收

- 同一候选可同时观察到三席并发请求，不必等整轮结束。
- 单席先返回时立即显示，其他席位仍显示请求状态。
- 真实反对意见显示依据；请求失败不显示为反对。
- 补正只改变允许的字段，原判断与原文可追溯。
- 同一候选多轮、多版本和多个数据源不串票。
- 审核中、等待对账、处理结束但审核未齐、三席齐全等状态均可辨认。
- 页面刷新和切换不会再次触发审核，监控不会覆盖人工草稿。
- 从实验库可以看到本次30条进度，实验库仍保持只读，生产记录不变。
