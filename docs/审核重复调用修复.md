# 审核重复调用修复

本次只控制重复请求，保持现有 DeepSeek 思考强度、生成参数、证据内容和三模型投票门槛。

## 请求复用与并发去重

`review_agent/request_cache.py` 通过 SQLite 的 `validation_requests` 表为同一冻结模型请求建立唯一预留。缓存键包含候选及 revision、文档和本体版本、完整实际输入、证据包哈希、审核提示与契约、记忆快照、委员会版本及成员、模型/家族/接口、凭据指纹和请求命名空间。不保存明文凭据。

- 正常重跑时，已完成且契约、引用均有效的模型票直接复用，只重新请求失败模型。`uncertain` 也复用，不能反复重投以挑选有利结果。
- 并发的相同请求等待已有请求结束，不额外向模型服务发送请求。SQLite 事务负责协调独立进程。
- 复用票重新绑定当前 audit、round、proposal_digest，并记录原票的 `cache_source`；任何冻结输入变化都会失效。新增有效证据后的必要复审仍重新调用完整委员会。
- 缓存命中记录 `actual_calls=0`，不复制旧请求的 attempts 和 Token 用量；原始调用记录留在来源审核中。
- 显式强制重审（CLI `--force` 或工作台强制重审）使用新的批次命名空间，仍会发出新的请求。

## 超时和未知结果

审核模型和规划模型超时、连接中断且没有确定的 HTTP 响应时，不再自动发送下一次重试。即使本地等待结束，远端请求仍可能产生费用，不能将其视为没有发送过。

审核请求超时标记为 `unknown`；进程在发送前后中断、尚未保存结果时保留 `running` 预留。不会因为锁过期就自动重发。再次遇到同一输入时返回 `DUPLICATE_REQUEST_SUPPRESSED`，进入证据/投票不足的人工路径。需要核对后由人工显式强制重审。

已确定的 HTTP 错误保留有限重试规则；402 不重试并暂停批次，充值后可以重新提交任务。JSON、契约和引用的纠错重试仍受原有次数与预算约束。

## 提交和持久化

- 同一批候选的重复活动任务提交复用同一个 queued/running job；候选 ID 去重排序。
- 候选真正启动前再次检查健康审核，避免排队期间其他任务已完成仍重复运行。
- 同一票据重复持久化不会再次追加 attempts，防止日志和成本统计被重复放大。
- 检查点恢复校验实际委员会成员，模型切换后不复用旧委员会状态。

数据库迁移版本为 3。下次正常初始化时创建新表，保留原有候选、审核、投票与人工标签。旧记录没有完整请求身份，不能安全自动回填为请求缓存；已有完整健康审核仍通过原有检查跳过。

## 验证

离线测试覆盖跨审核复用、并发单次发送、只重试失败模型、用量不重复计入、新证据完整重审、未知结果禁止自动重发、重复任务与票据持久化、显式强制重审。使用模拟模型和本机 HTTP 服务，不产生外部模型费用，也不启动生产审核。

最终完整 Python 回归：136 项全部通过。四模型故障恢复样例中，第一轮 4 次调用、恢复时仅补 1 次失败模型，总计 5 次，其他 3 票复用；新增证据样例仍完整调用两轮共 8 次。上述为离线工程验证，不代表线上审核准确率或固定节费比例。
